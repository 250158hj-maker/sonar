## 2. 呼び出しの形

### 2-1. 1問目は LLM を呼ばない

**気分ごとに用意した固定文をそのまま出す**（`mock/script.js` の `MOODS[*].opener`）。

| mood | label | 1問目（固定文） |
|---|---|---|
| `chat` | なんとなく話したい | 最近、ちょっと気になったことって何かありますか。 |
| `listen` | 聞いてほしいことがある | 何があったか、はじめから聞かせてもらえますか。 |
| `fog` | もやもやしている | そのもやもやは、何をきっかけに出てきましたか。 |
| `sort` | 考えを整理したい | 整理したいのは、どのことについてですか。 |
| `none` | 選ばずに始めた | 最近、印象に残っていることってありますか。どんな小さなことでも。 |

**理由は3つ。**

1. **入口に3秒の待ちが存在しなくなる。** 気分をタップした直後に問いが出る。§7 の「初回トークン3秒」は2問目以降だけの話になる
2. **API コールが1回減る。** 6ターンの会話なら6回が5回になる
3. **§1 の「テンプレは人間が設計する」と整合する。** 1問目は文脈がゼロで、LLM に書かせても人間が書いた固定文と差が出ない

`fog` の1問目が「そのもやもやは」で始まるのは、**本人が選んだ言葉をそのまま問いに織り込んでいる**からである（`mock/README.md` §3）。§3 で LLM に課す規則を、気分の選択にも先に適用してある。

### 2-2. 2問目以降は1回の呼び出し・素のテキスト出力

**LLM が返すのは「次の問い」の本文だけ。** JSON でも、ラベル付きでもない。

```
去年の冬から考えていて、先月まで続けた。その間、辞めずにいたのは何が理由でしたか。
```

サーバは SSE のデルタを**連結してそのままブラウザへ流す**。加工しない。[設計書 システム構成](system.md) §3(c)「中継であって、蓄積ではない」がそのまま成立する。

### 2-3. 深掘り判定を出力させない（2026-08-27 決定）

当初は「このまま掘り下げるか、別のテーマへ移るか」の判定を、問いとは別の出力として持たせる設計だった（[スコープと縮退ライン](../scope.md) §1、2026-08-26）。**これを廃止する。**

**判定結果の行き先が存在しないためである。**

| 行き先の候補 | なぜ受け取らないか |
|---|---|
| ノードの親（分岐） | 会話内のノードの親は**常に直前のノード**。掘っても移っても `parent_id` は変わらない（→[設計書 データベース](database.md) §6-4） |
| 画面 | 判定結果はユーザーに提示しないと決めている（→[スコープと縮退ライン](../scope.md) §2） |
| 地図の縦位置 | 深さは**根からの距離**で構造的に決まる。AI の判断を一切必要としない（→同 §2） |

**掘るか留まるかの差は、問いの文面そのものに現れる。** モデルは掘り方を*実行*すればよく、*名乗る*必要がない。名乗らせれば、その分のトークンを払って捨てることになる。

[設計書 システム構成](system.md) §5 の `Questioner` トレイトは、返り値が問いの文字列だけで、**最初から判定を出せない形になっていた**。この決定はその追認にあたる。

### few-shot は書き下ろしていない

例1〜3 は `mock/script.js` の `QUESTIONS`（64〜93行）から抜いたものである。あの6問は「直前の発話を織り込んだ問い」の見本として書かれており（`mock/README.md` §2）、**そのまま few-shot として使える**。

これは**モックを作り込んだことの2つ目の見返り**である（1つ目は `layout()` の座標計算が実装に持ち越せること。→[スコープと縮退ライン](../scope.md) §6）。

3例に絞ったのは、①語の反復 ②複数の要素の突き合わせ ③本人の言葉の引用、という**異なる3つの型**を1つずつ見せるため。同じ型を増やしてもトークンが増えるだけになる。

### 指示と few-shot が食い違うと、few-shot が勝つ（2026-08-27 実測）

初版の §3 には「60〜100字」「疑問符は1つ」と書いてあったが、**few-shot の3例はどれも34/47/29字で、すべて「。」で終わっていた**。実測5件は例のほうに完全に従い、字数は34〜56字、疑問符は0個だった。

**間違っていたのは指示のほうである。** モックの `QUESTIONS` は日本語として自然な長さと語尾で書かれており、「60〜100字」「疑問符」は英語圏の感覚を持ち込んだ誤りだった。指示を実測値に合わせて直した。

**教訓：例と指示が矛盾したら、直すのは例ではなく指示である。** 例は「実際に良いと判断した出力」であり、指示は「そう思っていること」にすぎない。

**ただし逆向きの修正が1回だけある**（2026-08-27、巡目2）。例3は元は「その限界を、誰かに言えていましたか。」で、**これは「はい／いいえ」で答えられる**。§9 の実測で Yes/No 型が最大の failure mode と分かったため、**規則を優先して例のほうを差し替えた**。

例を直すのは、**規則が例より強い根拠を持つとき**に限る。ここでは §2 の一線（AIに断定させない）が根拠であり、例の座りの良さより重い。

## 4. 気分を、掘り方の指示に変える

入口で選ばれた気分（5値）を `{steer}` の1行に変換する。**モックの `MOODS[*].steer` は4〜8語の断片**（「掘り下げない。同じ深さで横に広げる」）なので、プロンプトに入る文として書き下ろす。

| mood | `{steer}` に入る文 |
|---|---|
| `chat` | 深めない。直前の話題と同じ深さで、隣にあることを聞く。「なぜ」を聞かない。 |
| `listen` | 話題を変えない。同じ出来事の続きを促す。 |
| `sort` | 深めてよい。話し手が挙げた要素どうしを突き合わせて、選んだ理由の側を聞く。 |
| `fog` | 一歩ずつ深める。 |
| `fog`（直前の回答が短いとき） | 深めない。同じ深さで、いま出ている言葉について聞き直す。 |
| `none` | 一歩深める。 |
| `none`（直前の回答が短いとき） | 深めない。同じ深さで別のことを聞く。 |

### 「本人が引いたら止める」を、観測できる事実に翻訳する

`mock/README.md` §3 の `fog` は「**慎重に掘る。本人が引いたら即座に止める**」だった。これをそのままプロンプトに入れると、**AI が「引いた」を判定する**ことになる。本人の内面についての判断であり、[スコープと縮退ライン](../scope.md) §2 の一線に触れる。

そこで「引いた」を「**直前の回答が短い**」という観測可能な事実に置き換える。文字数なら、AI の解釈は一切入らない。

**しかも文字数を LLM に数えさせない。** サーバ側で数えて `{steer}` そのものを差し替える。

```rust
// 擬似コード。steer はコード側の定数（→設計書 データベース §5）
const SHORT_ANSWER_CHARS: usize = 20;

fn steer(mood: Mood, last_answer: &str) -> &'static str {
    let short = last_answer.chars().count() < SHORT_ANSWER_CHARS;
    match (mood, short) {
        (Mood::Chat,   _)     => "深めない。直前の話題と同じ深さで、隣にあることを聞く。「なぜ」を聞かない。",
        (Mood::Listen, _)     => "話題を変えない。同じ出来事の続きを促す。",
        (Mood::Sort,   _)     => "深めてよい。話し手が挙げた要素どうしを突き合わせて、選んだ理由の側を聞く。",
        (Mood::Fog,    false) => "一歩ずつ深める。",
        (Mood::Fog,    true)  => "深めない。同じ深さで、いま出ている言葉について聞き直す。",
        (Mood::None,   false) => "一歩深める。",
        (Mood::None,   true)  => "深めない。同じ深さで別のことを聞く。",
    }
}
```

- **LLM に条件分岐を任せない。** 「短ければ深めるな」と書いて守らせるより、短いときは「深めるな」としか書かれていない指示を渡すほうが確実
- **`SHORT_ANSWER_CHARS = 20` は暫定値。** §9 の実測で調整する
- **縮退可能。** 実装が詰まったら、気分だけで決まる固定 `{steer}` に戻せる（分岐を捨てるだけ）

`chat` / `listen` / `sort` に分岐が無いのは、**本人が申告した温度をこちらの都合で覆さない**ため。「聞いてほしい」と言った人の回答が短くても、話題を変える理由にはならない。

## 5. messages の組み立て

履歴は「**根からそのノードまでのパス**」であって、会話の全ノードではない（→[設計書 データベース](database.md) §6-5）。

| DB のノード | Messages API |
|---|---|
| `node.question` | `{"role": "assistant", "content": <question>}` |
| `node.answer` | `{"role": "user", "content": <answer>}` |

`created_at` 昇順に並べ、`question` → `answer` の順で交互に積む。**最後は必ず `user`（本人の最新の回答）で終わる**ので、続きを書くのは assistant ＝ 次の問いになる。

1手目の `question` には §2-1 の固定文がそのまま入っているので、**LLM から見ると1問目も自分が書いたことになっている**。特別扱いはいらない。

### 3ノード目を答え終えた時点の例

```json
{
  "model": "claude-haiku-4-5",
  "max_tokens": 300,
  "stream": true,
  "system": "<§3 の全文。{steer} は展開済み>",
  "messages": [
    {"role": "assistant", "content": "そのもやもやは、何をきっかけに出てきましたか。"},
    {"role": "user",      "content": "三年続けたバイトを先月辞めた"},
    {"role": "assistant", "content": "三年続けたバイトを辞めたんですね。辞めると決めたのは、いつ頃でしたか。"},
    {"role": "user",      "content": "去年の冬くらいから考えてはいた"},
    {"role": "assistant", "content": "去年の冬から考えていて、先月まで続けた。その間、辞めずにいたのは何が理由でしたか。"},
    {"role": "user",      "content": "店長が良い人で、抜けたら回らないのが分かってた"}
  ]
}
```

**会話 ID もノード ID も送らない。** LLM に必要なのは問いと回答の並びだけで、識別子は問いの生成に寄与しない。

## 6. リクエストのパラメータ

| 項目 | 値 | 根拠 |
|---|---|---|
| `model` | `claude-haiku-4-5` | [ADR-0002 LLMプロバイダ選定](../adr/0002-llm-provider.md)。日付サフィックスは付けない |
| `max_tokens` | `300` | 出力60〜100字 ≒ 120トークン。途中で切れないよう余裕を持たせる。上限であって目標ではない |
| `stream` | `true` | §7 の初回トークン3秒。全文完了を待たない |
| `system` | §3 の全文 | 会話ごとに変わるのは `{steer}` の1行だけ |
| `temperature` | **指定しない** | 下げると毎回同じ形の問いが出て、台本感が戻る。既定のままでよい |
| `thinking` | **付けない** | →§11 |
| `output_config` | **付けない** | →§11 |
| `cache_control` | **付けない** | →§11 |

**ヘッダは `x-api-key` / `anthropic-version: 2023-06-01` / `content-type: application/json` の3つだけ。** ベータヘッダを使う機能を1つも採っていない（→§11）ので、`anthropic-beta` は付かない。

### SSE の受け取り

`content_block_delta` の `delta.text` を連結すると、それが問いの全文になる。

```
event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"去年の冬"}}
```

**`message_delta` の `usage.output_tokens` と `message_start` の `usage.input_tokens` を記録する。** §10 の試算を推定のまま置かないため。

## 7. 尋問にしないための書き方

**相槌を消すと、設計を誤れば尋問になる**（[スコープと縮退ライン](../scope.md) §2）。プロンプト側の手段は3つ。

| # | 手段 | 効き方 |
|---|---|---|
| 1 | **few-shot 3例**（§3） | 主役。「こう書け」を文章で説明するより、3つ見せるほうが速く正確に伝わる |
| 2 | **「直前の回答の語を、言い換えずに1つ以上そのまま使ってから問う」** | 検査可能なルールになっている（→§9）。「自然な会話にせよ」のような測れない指示を置かない |
| 3 | **1ターンに問いは1つ・疑問符も1つ** | 問いを重ねると、答える側は取り調べを受けている形になる |

2 が中核である。`mock/README.md` §2 は「**自分の言葉が問いに反復されること自体が『聞いていた』の証明になる**」と書いた。これはUIの主張ではなく、**プロンプトの規則に落とせる主張**だった。

## 8. 断定を出させない

### 規則は1つだけ

> **話し手がまだ言っていない言葉を、問いの中に出さない。**

禁止事項を並べるより、この1文のほうが効く。理由は**検査可能な形をしている**ことである。

| 書き方 | 検査できるか |
|---|---|
| 「診断をするな」 | できない。どこからが診断かの線が引けない |
| 「本人が言っていない言葉を出すな」 | **できる。**履歴に無い語が問いに出たかどうかで判定できる |

そしてこの規則は、[スコープと縮退ライン](../scope.md) §2 が挙げた4つの❌をすべて塞ぐ。「安定を大切にする方だと思いますが」が禁止されるのは、それが診断だからではなく、**「安定」を本人がまだ言っていないから**である。

### ❌⭕の対照表をそのまま入れる

§3 の「書いてはいけないこと」は、正典 §2 の表を移植したものである。**書き換えずに移植する**のが要点で、正典の表現とプロンプトの表現がずれると、どちらが正なのか分からなくなる。

とくに3行目（「安定を大切にする方だと思いますが、それはなぜですか」）は落とせない。**問いの中に断定を密輸する経路**であり、正典 §2 が「落とし穴が2つある」の1つ目に挙げたものである。

### いちばん危ないのは「うなずかせ」（2026-08-27 実測で発見）

§9 の実測で、設計書のどこにも書いていなかった失敗モードが出た。

> AI「気まずい雰囲気になるというのは、**自分に対して何かが向けられるのが嫌だったんですか**。」
> 本人「**うん**」

**地図に残るのは「うん」である。**

正典 §2 は「マップに残るものは本人の発話。AI の生成文ではない」と決めた。この会話は**文字列としてはその通り**——`node.answer` に入るのは本人が打った「うん」である。しかし**中身は AI が与えた解釈への同意**にすぎない。

| | 見え方 | 実際 |
|---|---|---|
| DB | 本人の発話が入っている | 内容は AI の解釈 |
| 画面 | 異常なし | 異常なし |
| 地図 | 点が1つ増える | 増えた点は本人の言葉ではない |

**どこにも異常が出ない。** 検査でしか見つからない種類の破れ方であり、だからこそ §9 が要る。

**発生条件がさらに悪い。** 実測では**本人が抽象的なことや気持ちを言った直後**に集中した（「気まずい雰囲気になるのかなと」「安心感がありました」）。つまり**深いところに近づくほど出る**。§2 の一線は、まさにそこで守られなければ意味がない。

**対処は形の規則で行う**（→§3）。「解釈を出すな」は測れないが、「**はい／いいえで答えられる問いにしない**」「**二択を並べない**」は形で判定できる。うなずかせるには、まず Yes/No か二択の器が要る。**器を禁じれば、中身も入らない。**

### プロンプトに書くだけでは漏れる

正典 §8 はこの前提を最初から書いている。**したがって検査の手順を設計の一部として持つ**（→§9）。

## 9. 検査手順

**状態：21/25問を実施し、巡目2で打ち切り（2026-08-27）。** →下記「机上の検査はここで打ち切る」

### なぜ手順を設計に含めるか

正典 §8 は論点として「制約の書き方**と、実出力の検査手順**（プロンプトに書くだけでは漏れる）」と書いていた。**書き方だけ決めて検査を持たないなら、この論点は解けていない。**

自動で止める方式は採らない。SSE で1文字ずつ出している以上、**全文が揃う頃には既に画面に出ている**。表示を止める仕組みを作ると、逐次表示という §7 の要件そのものと衝突する。

### 手順

**気分5種 × 各5ターン ＝ 25問**を実際に生成させ、目視でチェック表を埋める。

1. **1ターン目の回答だけ固定**する（下表）。ここを固定するのは、5種の入口を同じ条件で比べるため
2. **2ターン目以降は、返ってきた問いにその場で実際に答える**。台本を続けると噛み合わない文脈で問いを評価することになり、実際の使われ方から離れる
3. `fog` と `none` では、**20字未満の短い回答を1回わざと混ぜる**。§4 の分岐が効いているかを見る

|---|---|
| `chat` | よく通る道にあった店が、いつのまにか閉まってた |
| `listen` | 先週、親と久しぶりに言い合いになった |
| `fog` | 断りたかったのに、その場で言えなくて引き受けてしまった |
| `sort` | 来年どうするかを決めないといけないんだけど、まだ決まってない |
| `none` | 久しぶりに会った友達が、思ってたより元気そうだった |

> **【注意】キャッシュのために `system` を膨らませない**
> Haiku 4.5 の最小キャッシュ長は4,096トークン。現在1,130なので、あと3,000トークン足せばキャッシュが選択肢に入る——**という考え方をしない**。入力を増やしてから10%引きにするより、増やさないほうが安い。§11 の判断は変わらない。

### 要約を採らない理由は、コストではない

§7 は「コスト超過時の**最初の手段**は入力トークンを減らす（全文再送 → 要約＋直近数ターン）」と書いている。**この手段は発動しない**——超過していないからである。

そのうえで、要約には設計上の代償がある。

> **要約は AI が書いた文章であり、それを文脈に入れると、以降の問いは「AI の言い換え」を根拠に作られることになる。**

正典 §2 は「マップに残るものは本人の発話。AI の生成文ではない」と決めた。**文脈も同じ扱いにする。**安くする必要が無い以上、一線に近づく理由がない。

### 地図に入るテキストの出所（正典 §8 の残り1件）

**本人の発話をそのまま置く。AI の言い換えは置かない。**（2026-08-27 確定）

言い換えを置くなら「この言葉で残していいですか」と確認するターンが要る。**ターンが1つ増えることは、入力コストを下げるというゴール（→§1）と正面から逆行する。**確認せずに置けば、§2 の一線を越える。

この結論は [設計書 データベース](database.md) §5（`summary` カラムを持たない）と `mock/README.md` §5 に既に現れており、正典 §8 に未確定として残っていたのは書き漏れである。

## 11. 検討して採らなかった案

| 案 | 採らない理由 |
|---|---|
| **構造化出力**（`output_config.format`） | 出力が JSON になると、**SSE に流れるのも JSON のトークン**になる。ブラウザで部分 JSON を解くか、サーバで組み立て直すかのどちらかになり、後者は [設計書 システム構成](system.md) §3(c)「問いの本文をサーバ側で組み立て直さない」を破る。そもそも §2-3 で分離すべき値が無くなった。（Haiku 4.5 は構造化出力に対応しているので、使えないから避けたのではない） |
| **判定と生成を2回の呼び出しに分ける** | 履歴を2回送ることになり、初回トークンまでの時間に判定1回分が丸ごと乗る。§7 の3秒とコストを**両方**悪化させて、得るものが §2-3 の判定＝行き先の無い値である |
| **出力1行目にマーカーを出させ、サーバが剥がす** | 1回の呼び出しのまま判定を記録できるが、**剥がし損ねると `DEEPEN` が画面に出る**事故経路が1つ増える。消費者のない値のために経路を増やさない |
| **要約＋直近数ターン** | →§10。超過していないうえ、AI の言い換えが文脈に入る |
| **プロンプトキャッシュ** | **Haiku 4.5 の最小キャッシュ長は 4,096トークン**（2026-08-27 確認）。§3 は約900トークンで桁が足りない。`cache_control` を付けても**エラーにならず無言で効かない**（`cache_creation_input_tokens: 0` が返るだけ）ので、「効いているつもり」になるほうが危険。→[ADR-0002 LLMプロバイダ選定](../adr/0002-llm-provider.md) §5 を訂正済み |
| **`thinking`** | 初回トークン3秒を直撃する。出力100〜150トークンの仕事に推論は要らず、Haiku 4.5 の `budget_tokens` は最小1024なので**思考のほうが出力より長くなる** |
| **`temperature` を下げる** | 問いの形が毎回同じになり、モックが避けた「台本に見える」状態（→[スコープと縮退ライン](../scope.md) §1）に戻る |
| **system を英語で書く** | トークンは減るが、差は1ターンあたり数百トークン＝1会話で $0.002 程度で、判断を動かさない。**本人が読めてプレゼンでそのまま見せられる**ほうが価値が大きい |
