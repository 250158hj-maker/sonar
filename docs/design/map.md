	│                     ├─ ② 問いと回答をくり返す

	│                     └─「地図を見る」→ map.html

## 設計の意図

企画書・スコープと縮退ラインで決めたことを、画面の形で表現している。

### 1. チャットアプリに見せない

**AI の発話は「問い」だけで、相槌・共感・感想を出さない**と決めている。
これを普通のチャットバブルの往復で作ると、返事が来ないまま質問だけが飛んでくる **尋問** に見える。

そこで対話画面は「問いが1つ、静かに現れる」構成にした。

- 現在の問いは**入力欄のすぐ上**に大きく置く
- 済んだやりとりは**小さく薄くなって上へ押し上げられる**（＝沈んでいく）
- AI のアイコンや吹き出しは置かない

### 2. 傾聴は相槌ではなく「問い」で示す

相槌が無い代わりに、**問いに直前の発話を織り込む**。

> ユーザー「三年続けたバイトを先月辞めた」
> Sonar「**三年続けたバイトを辞めたんですね。**辞めると決めたのは、いつ頃でしたか。」

自分の言葉が問いに反復されること自体が「聞いていた」の証明になる。
`script.js` の `QUESTIONS` は、この形になるよう全問を書いている。

### 3. 入口は「気分をタップ1回」

会話の最初に、選択式で今の気分を1回だけ聞く。

**これは追加の一手間ではなく、最初の問いをタップ1回に置き換えるもの。** いきなり自由記述の問いが来るより入口が軽い。

| 選択肢 | AIの振る舞い（`MOODS[*].steer`） |
|---|---|
| なんとなく話したい | 掘り下げない。同じ深さで横に広げる |
| 聞いてほしいことがある | 遮らない。話題に留まって続きを促す |
| もやもやしている | 慎重に掘る。本人が引いたら即座に止める |
| 考えを整理したい | 積極的に掘ってよい |

**「どれくらい深く話したいか」は直接聞かない。** それを聞くと、表に出さないと決めた深さの仕組みを入口で見せてしまう。気分を聞いて、深さは内部で導出する。

選んだ言葉はそのまま1問目に織り込まれる。「もやもやしている」を選ぶと、1問目は **「そのもやもやは、何をきっかけに出てきましたか。」** になる——2 の「傾聴は問いで示す」を、気分の選択にも適用している。

`steer` は本実装でプロンプトに渡す指示であり、**画面には出さない**。

### 4. 深さはユーザーが決める

- **「ここまでにする」を常に見える位置**に置き、やめることを後ろめたくさせない
- 途中でやめても「未完了」扱いにしない。答えた分だけ点が置かれる
- **段数を表示しない。** 掘る積極性は内部で決まり、画面に出さない
- **ホーム画面に到達度の数字を置かない**（2026-08-30 決定）。「いちばん深く掘り下げた回数」を消した。
  減らない数字を最初の画面に置くと、**この節で消したはずの「もっと深く掘らねば」という圧力を、入口で作り直す**ため。
  残した2つ（話した回数・地図に残った言葉）との違いは単調増加かどうかではない——**あれは「自分の言葉がどれだけ残ったか」という量**であり、
  消したのは**「どこまで深く降りたか」という到達度**である。量は§1のゴール（自分の言葉が残る）の実績で、到達度は本人が決めた深さの採点になる

### 5. 地図に残るのは本人の言葉だけ

まとめ画面の点も、地図のラベルも、**実際に答えた回答文からそのまま作っている**。
AI に要約させると地図に AI の言葉が混ざるため、そうしていない。
2問だけ答えて終われば、点は2つしか置かれない。

### 6. 別々の会話のノードは合流させない

同じ話題が複数の会話に出てきたとき、それを1つのノードにまとめる案があったが、**やらないと決めた**（2026-08-26。→ `adr/ADR-0003`）。

理由は2つ。

1. **縦軸の定義が壊れる。** 合流させると木ではなく DAG になり、根からの距離が経路によって変わる。「縦の位置＝掘り下げた回数」が一意に決まらなくなる
2. **AIの断定になる。** 「この2つの発話は同じ話題だ」は AI の判断であり、7 でラベル付けを拒否した理由（＝分類は弱い断定）がそのまま、より強い形で当てはまる

結果としてデータは常に**木**であり、深さが一意に決まり、レイアウトに tidy tree がそのまま使える。DBでもノードの親は1つで済む。

### 7. 縦軸＝深さ。ただしカテゴリ名は付けず、段数にも上限を置かない

地図は「どこまで深く辿ったか」が一目で分かることを最優先にした。

- **縦の位置＝根からの距離**（その話題を何回掘り下げたか）
- 色も深さに対応（淡い青灰 → シアン → 琥珀）
- **深さのグラデーションは SVG の内側に置いている。** ページ側に置くと、図の縦位置と背景の暗さがズレて意味が壊れる
    - **訂正（2026-08-31 実測）：この意図は実現できていなかった。** `#bg` の矩形が
      `x=-20000 y=-20000 width=40000 height=40000` で、可視範囲はグラデーション全体の
      **約1.2%**（オフセット 0.498〜0.510）にあたる。`--chart-top` も `--chart-bot` も
      画面に出たことがない——実質単色である。実際に見えている縦のグラデーションは
      `.map` 側の `linear-gradient(180deg, ...)`（→[詳細設計書](../detail.md) §7）

**「出来事」「選択」「信念・感情」というカテゴリ名は付けない。** 理由は2つ。

1. **必ず3回で深いところまで行けるとは限らない。** 2回で着くこともあれば9回かけても届かないこともあるのに、固定の段で切ると必ず嘘になる
2. **ラベルを貼る行為は、本人の発話を分類すること＝弱い形の断定**にあたる。AIに「あなたの信念は〇〇です」と言わせないと決めておきながら、地図で同じことをやってはいけない

**同じ理由で、段数そのものにも上限を置いていない。**

- 目盛り線は固定本数ではなく、**いま出ている最大の深さまで JS が引く**
- 色は段ではなく連続量。`depthT(d) = 1 - 0.68^d` は 1 に漸近するだけで到達しないので、何段でも「前の段より深い色」になる
- 実際の色は CSS の `--d-shallow` / `--d-mid` / `--d-deep` を `color-mix()` で補間して作る。**JSは色を持たない**（持たせるとライト／ダークに追従しなくなる）
- **対話画面の背景も同じ `depthT()` に載せた**（2026-08-30 統一）。もとは2ターンごとに切り替わる3段のパレットで、**3段目で頭打ち**していた——7ターン目と20ターン目が同じ色になる状態であり、すぐ上の1（固定の段で切ると必ず嘘になる）と正面から矛盾していた。いまは地図のノードと同じ連続量（`--t`）を読むので、**深さの表し方がアプリ全体で1つ**になっている

カードもカテゴリ名を出さず、「この話題を N 回掘り下げたところ」という事実だけを書く。
まとめ画面は縦軸が無いので、**字下げと色**で深さを示す。こちらも上限は無い。

### 8. 会話が増えても壊れないよう、会話単位で畳む

地図は**全会話を1枚に蓄積する**。すると会話を重ねるほどノードが増えていく。
全部を一度に描くと、点の間隔が指の幅を下回り、隣を押してしまう。

そこで、**全体表示に出すのは各会話の1手目だけ**にした。

| 状態 | 見えるもの |
|---|---|
| 全体表示 | 根＋各会話の1点。会話が並んでいるのが見える |
| 会話を押した | その会話の枝だけが開く。他の会話は畳まれたまま残る |
| 点を押した | その点にズームして、そのとき言った言葉が出る |

**1画面の点の数が「ノード総数」ではなく「会話数」で決まる**ので、
会話1回あたり3〜6ノード増えても、全体表示の密度はその1/3〜1/6でしか増えない。

畳んだ会話が点として残り続けるのが要点で、**会話が並んでいること自体が地図の中身**になる。

それでも会話数そのものは増え続けるので、次の2つで受ける。

- **縮尺に下限を設ける**（`MIN_GAP_PX = 58`）。点の間隔が58pxを切るところまでは引かない
- **入り切らない分はドラッグで動かす**（パン）。ホイールでも拡大縮小できる

40会話（159ノード）で確認したところ、全体表示に出るのは41点、点の間隔は58px、当たり判定は48pxで、重ならずに保たれた。

### 9. 大きさは画面px基準、位置だけが世界座標

点・当たり判定・文字を SVG の座標のまま持つと、引くほど小さくなって読めず押せなくなり、寄ると当たり判定だけが巨大になる。

そこで **位置だけを世界座標に置き、大きさは画面px基準**にした。

- JS が `--s`（画面1pxが何ユーザー単位か）を `viewBox` の更新ごとに書き込む
- CSS 側は `calc(24px * var(--s))` のように書く。これで「画面上で常に24px」になる
- 線は `vector-effect: non-scaling-stroke` で同じことをする

結果として、**倍率がいくつでも当たり判定は直径48px、ラベルは13px**で一定になる。
（以前は SVG のユーザー単位で持っていたため、横長の画面ではラベルが実効7.4pxまで縮んでいた）

### 10. 地図は画面いっぱい。点を押すとそこへズームする

地図はページの中の一要素ではなく、**画面そのもの**として置く（`.stage` がヘッダー以外の全部を占める）。余白を作らない。

- `viewBox` を `requestAnimationFrame` で補間して寄る（`animateTo()`）
- 押した点は画面の縦中央に来る（`NODE_Y = 0.5`）。カードは下端に固定なので、点は中央でよい
- 倍率は `ZOOM = 0.62`。寄りすぎると周囲の枝が消えて「どこから来た点か」が分からなくなるので、親ノードが視界に残る程度に留める
- ズーム中は他の点を薄くし、案内文を消す。見るべきものを1つにする（**凡例「縦の位置＝掘り下げた回数」は 2026-08-30 に廃止**。→11 の (c)）

**`viewBox` の縦横比を表示領域に合わせている**（`fitView()`）のが要点。合わせないとレターボックス（上下または左右の余白）が出て、地図が実際より小さく見える。

**縦が余ったら上に寄せる。** 中央に置くと木の上下に均等な余白ができるが、この地図は「上が浅瀬・下が深海」なので、余った水は**下**にあるべき（＝まだ潜っていない深さ）。

### 11. ラベルは「いつ出すか」で制御する（意味的ズーム）

全ラベルを常に出すと、ノードが増えたとき読めない塊になる。かといって全部消すと、地図は「探れるが見渡せない」ものになる。

そこで、**出す量を「読める量」に収まるところで切り替える**。

判定は2つの掛け合わせ。

**(a) 出す対象を絞る**

| 状態 | ラベルを出す対象 |
|---|---|
| 全体表示 | **なし**（根「わたし」だけ）。形・量・深さを見る状態 |
| 会話を開いている | **その会話の点だけ。** 畳んだままの会話は点のみ |
| いつでも | 触れた／フォーカスした点、および根（わたし） |

畳んだ会話の点は「まだ読んでいない場所」の目印であって、いま読む対象ではない。開いている会話に寄ると畳んだ点が横に詰まるので、全部に出すと上端で重なって潰れる。

> **【注意】全体表示で全ラベルを出していたのを取りやめた（2026-08-30）**
> もとは「全体表示の点は会話の数しかないので、読める量に収まる」と見積もって全部出していた。**見積もりが外れていた。**
>
> 横814pxで実測すると、点の間隔は **94.7〜117.0px**——すべて (b) の閾値 80px を超えるのでラベルが出る。ところが**ラベル本文の幅は 97.6〜157.6px** で、7本中4本が最小間隔より広い。**間隔の判定は通るのに、文字は隣へはみ出していた。**
>
> **(b) が測っていたのは点の間隔であって、文字の幅ではない。** 最大幅157.6pxが収まるには画面幅がおよそ1200px要る計算で、それ以下では必ず重なる。
>
> 直し方は閾値を上げることではなく、**出すのをやめること**にした。正典 §6 が最初から「**引いているとき＝形・量・深さだけ**、点に触れたとき＝その1つ、寄ったとき＝周辺の言葉」と書いており、**ずれていたのは実装のほう**だったため。どの会話かは、点に触れれば読める。

**(b) 横幅が足りているかを測る**

`setView()` で「1点あたり画面上に何pxあるか」を計算し、`LABEL_MIN_PX = 80` を下回ったらラベルを消す（`data-detail`）。**効くのは会話を開いているときだけ**になった（全体表示は幅によらず出さない。→上の警告）。

- **点の数でも倍率でもなく、実際の横幅で決める。** 守りたい原則は「出す量を、読める量に収める」なので、点が少なくても狭い画面なら出さない
- **測る対象は (a) で出すと決めた点だけ。** 出す気のない点の間隔で判定すると、読める会話の言葉まで消える
- 押せる下限（`MIN_GAP_PX = 58`）とは別の値。**押せる < 読める** なので、その間の倍率では「点は押せるがラベルは出ない（＝地形図）」状態になる
- **同じ弱点（間隔しか見ていない）は会話を開いたときにも残っている。** ただし同時に出る点は縦に散るので横方向でぶつかりにくく、いまの実測では問題になっていない。**本当に直すなら測るべきは `getBBox().width`** であって間隔ではない

**(c) 出さないものを、別の手掛かりで補う**（2026-08-30）

全体表示はラベルも案内文も出さない。**押せることは点の大きさで示す。**

| | 点の直径 | 輪の直径 |
|---|---|---|
| 全体表示 | **21.9px** | 37.9px |
| 会話を開いている | 13.9px | 25.9px |

**当たり判定（48px）の内側に収める。** 見た目が判定より大きいと、縁を押したのに反応しない場所ができる。

同時に、地図に重ねていた説明文を2つとも消した。

| 消したもの | 理由 |
|---|---|
| 「縦の位置＝掘り下げた回数」（凡例） | **図の左の「浅い／深い」が同じことを示している**ので重複。SVG の `aria-label` には残してあるので、読み上げでは辿れる |
| 「点を押すと、その会話が開きます」（案内） | 押せることは**文で説明するより点の大きさで示すほうが速い** |

**会話を開いたあとは点が増えて1つずつが小さく見える**ので、そちらには「点を押すと読めます」を残している。

### 12. 前後のノードへ、全体表示を経由せずに移動できる

点を1つ見るたびに全体表示へ戻るのは体験が悪い。ズーム中にカードの両脇へ前後ボタンを出す。

**辿る範囲は「開いている会話の中」だけ**にした。会話をまたいで進むと、いま誰のどの話を読んでいるのか分からなくなる。

**順序は深さ優先。** 木なので「次のノード」は分岐点で曖昧になるが、深さ優先で一列に並べればどこでも前後が1つに定まる。連鎖している間は 親 → 子 を辿るので、**そのときの会話を順に読み直すのと同じ動き**になる。分岐点では兄弟へ回る。

- 順序は `NODES` の `children` から実行時に組み立てる（`orderOf()`）。**本実装ではDBのノード親子関係がそのまま入る**
- `←` `→` キーでも移動できる
- **端では押せなくする。** 一周させると「今どこにいるか」の感覚が壊れる
- ボタンの `title` に移動先の発話を出すので、押す前に行き先が分かる

**戻るのも一段ずつ。** 背景か `Esc` で「点 → 会話全体 → 全部畳む」と1段ずつ戻る。一気に戻すと、いま地図のどこにいたかが分からなくなる。「全部を見る」ボタンだけは一気に戻る。

実装上の注意：`.detailbar` は `pointer-events: none`、その中のカードとボタンだけ `auto` にしている。**隙間を通したクリックは地図に届いて一段戻れる**ようにするため。

### 13. ライト／ダークは画面ごとに固定せず、本人が選ぶ

画面ごとに明暗が切り替わると、移動するたびに目が慣れ直すことになる。テーマとして分けた。

- ヘッダーに**太陽／月**のトグルを置く。押すと切り替わる先のアイコンが出る
- 選択は `localStorage`（`sonar-theme`）に残す。**未選択なら端末設定**（`prefers-color-scheme`）に従う
- 各HTMLの `<head>` にインラインスクリプトを置き、**描画前に適用**してちらつきを防ぐ

**どちらのテーマかの解決は、この `<head>` のスクリプトで済ませて `data-theme` に必ず書き込む。**
こうするとCSS側は `:root` と `:root[data-theme="dark"]` の2ブロックで済む。以前は同じ色を「`@media (prefers-color-scheme: dark)` 版」と「属性版」の2箇所に書いていて、片方だけ直す事故が起きる形になっていた。

**「深さ＝暗さ」をどう保つかが設計上の論点だった。** 答えは、明暗の絶対値ではなく**相対的な水深ランプ**として扱うこと。

| | 浅い | 深い |
|---|---|---|
| ライト | ほぼ白 | 中程度の青 |
| ダーク | 藍 | ほぼ黒 |

どちらも「降りていく」感覚は保たれる。

色はすべて `:root` のトークンに集約してあり、**SVGの中身もトークンで塗っている**（グラデーションの `stop-color`、ノードの `fill`、深さの目盛り線と軸）。**JSにもHTMLにもハードコードされた色は無い。**

## モックであるがゆえの制約

実装時に置き換わる部分。

| モックでの実装 | 本実装 |
|---|---|
| `QUESTIONS`（固定の6問） | **1問目は `MOODS[*].opener` の固定文のまま**、2問目以降は Claude API（`claude-haiku-4-5`）が生成する。この6問は **few-shot として本実装のプロンプトに移植する**（→[設計書 プロンプト](prompt.md) §2-1・§3） |
| `typeOut()`（1文字ずつ描画） | SSE の受信ハンドラ |
| `stopTyping()`（`clearInterval`） | **`AbortController.abort()`。** 途中で会話を終えたらSSEを止める。止めないと誰も読まない出力にトークンを払い続ける |
| `CONVERSATIONS` / `NODES`（固定データ） | DB（Toasty）から取得したノード |
| 手書き SVG の描画 | **そのまま移植する。** 外部ライブラリは使わない（2026-08-26 決定。→[スコープと縮退ライン](../scope.md) §6） |
| — | **`layout()` はそのまま使える。** 座標計算は描画ライブラリを入れても変わらない |
| 「例を入れる」ボタン | デモ用。実装には残さない |
| `MOODS[*].steer`（未使用の文字列） | プロンプトに渡す指示。**本実装では「気分 × 直前の回答の長さ」で差し替わる**（→[設計書 プロンプト](prompt.md) §4）。モックでは1問目の差し替えだけを再現している |

**自由入力しても、次の問いは固定のものが出る。** 問いは事前に書いたシナリオであり、入力内容に反応しているわけではない。

    - **訂正（2026-08-31 実測）：「数百件」は1桁ずれていた。実際は24本で入り切らなくなる**（→[詳細設計書](../detail.md) §6）。
