## 3. 決定の詳細

### 3-1. 開発は WSL2 で行う。Windows ネイティブの Rust は導入しない

Windows 側で Rust を通すには、VS Installer で C++ ワークロード（MSVC ツールセット＋Windows SDK）を追加する必要がある。数GBのダウンロードであり、**その時間は実装8日から直接引かれる**。

**どちらの道を選んでも C コンパイラは必須である。** Toasty の SQLite バックエンドは `rusqlite` 経由で C の SQLite をコンパイルするため、純 Rust では閉じない。WSL は既にそれを持っている。

> **【メモ】スパイク3の障害物は事前に潰れていた**
> [設計書 データベース](../design/database.md) §8 は「SQLite ならサーバプロセスが要らないので、スパイク3の障害物が1つ減る」と書いた。環境側でも同じことが起きている——C toolchain が揃っているので、`rusqlite` の bundled SQLite はそのままコンパイルできる。

**縮退**：WSL が壊れたら Windows に MSVC を入れる。これは「安く作り直す」の対象であって、中止ではない（→[スコープと縮退ライン](../scope.md) §0）。

### 3-2. コードは `~/workspace/sonar` に置く。`/mnt/c` には置かない

`/mnt/c` は **9P プロトコル越しのマウント**で、`msize=65536` の単位で Windows 側のファイルシステムと往復する。cargo のビルドは小さなファイルを大量に読み書きするため、ここでレイテンシが積み上がる。

**実装8日のあいだ、ビルドのたびに払い続ける種類のコスト**であり、初回に一度払えば済むものではない。

### 3-3. ドキュメントとコードは別リポジトリにする

| | 場所 | リポジトリ |
|---|---|---|
| ドキュメント | `C:\Users\250158\Desktop\obsidian\Vault\01_projects\06_sonar`（Windows。2026-08-31 に `06_個人開発` から改名） | `obsidian_vault` |
| コード | `~/workspace/sonar`（WSL） | **新規**（提出物⑦） |

提出物⑦は「プロジェクトのソースコード（GitHub）」であり、**Vault 全体を提出物にはできない**。

> **二拠点は WSL を選んだ代償ではない。提出物の要件から、もともと分かれるべきものである。**

この順序を取り違えると「WSL をやめれば1つにまとめられる」という誤った縮退案が出てくる。まとめられない。

### 3-4. `mock/` は一方向コピー。移植後は Vault 側を凍結する

[スコープと縮退ライン](../scope.md) §6 は「`mock/` のコードを移植する」を唯一の現実的な道と決めている（実装8日でマインドマップを新規に書く余裕が無いため）。**移植した瞬間、同じ JavaScript が2箇所に存在する。**

分担を先に決める。

| | 正典 | 移植後に直す場所 |
|---|---|---|
| **実装**（HTML / CSS / JS） | **Sonar 側**（`~/workspace/sonar`） | Sonar 側だけ |
| **設計意図**（13項目） | **Vault の `mock/README.md`** | Vault 側だけ |

`README.md` はコードではなく判断の記録なので、Vault に残しても二重管理にならない。**コードだけが移る。**

### 3-5. `ANTHROPIC_API_KEY` は Windows を一次情報とし、`WSLENV` で渡す

**キーの実体を2箇所に持たない。** 2箇所に置くと、ローテーションしたときに片方が古いまま残る。

> **【メモ】2026-08-31 追記：有効なキーは2本ある（自宅用・学校PC用）**
> Console で確認した結果、**有効なキーは2本で、どちらも意図したもの**である。旧キーの残存は無い（§5 の本人確認①はこれで解決）。
>
> | キー | 使う場所 |
> |---|---|
> | 自宅 | Windows の User 環境変数 → `WSLENV` → WSL2（本節の決定そのもの） |
> | 学校 | 学校で本人が使用している PC |
>
> **上の原則と矛盾しない。** 「実体を2箇所に持たない」は**1本のキーの値を2箇所に置かない**という意味であり、**用途ごとに別のキーを持つこと**は、むしろ各キーの実体を1箇所に保つ。
>
> **分けるほうが正しい理由は、失効の判断が独立になること。** 1本を2台で共有すると、片方が漏れたときの失効が「両方止まる」との天秤になり、**結果として失効させられなくなる**。分けてあれば片方だけ切れる。
>
> **ただし2本は同じ残高・同じ Spend limit を共有する**（→[設計書 プロンプト](../design/prompt.md) §13）。学校で試した分も 9/9・9/15 と同じ財布から出る。
>
> **残る作業2つ**
> - [ ] **Console のキー名を用途が分かる名前にする**（例：`home-wsl` / `school-pc`）。既定名のままだと、数週間後にどちらを消せばよいか分からなくなる。**失効を独立にした利点が、名前で消える**
> - [ ] **学校の PC を離れるとき（PC入れ替え・卒業）に、学校側のキーを Revoke する。** 自分の管理下から出る機械にキーを残さない

> **【メモ】前提を差し替えた（2026-08-30）**
> 当初は「`check/run.py` を Windows の python で動かすので、Windows 側にキーが要る」を理由にしていた。
> **本人確認により「動くのは WSL だけでよい」となった**ので、理由を置き換える。**決定そのものは変わらない。**

| 案 | 判断 |
|---|---|
| **Windows の User 環境変数 ＋ `WSLENV`** | **採用。** 実体は1箇所（レジストリ）。WSL 側は参照するだけで、**どのファイルにも書かれない** |
| WSL の `~/.bashrc` / `~/.zshrc` に `export` | **却下。平文でファイルに書く経路を作る**（下記） |
| リポジトリに `.env` | 却下。→[設計書 プロンプト](../design/prompt.md) §13「リポジトリには置かない」。git に載る事故経路を作らない |

> **【注意】シェルの設定ファイルには書かない**
> `~/dotfiles` は **GitHub リモート付きの git リポジトリ**で、`.zshrc` はその追跡下にある（2026-08-30 実測）。**シェル設定は「同期するもの」**なので、そこに `export` を1行置いた時点で、キーが公開へ向かう経路ができる。
>
> 環境変数をレジストリに置けば、**書き出されるファイルがそもそも存在しない。** これが `~/.bashrc` 案を却下する実質的な理由である。

**副産物**：Windows 側にキーが残るので、`check/run.py`（→[設計書 プロンプト](../design/prompt.md) §9）は Windows の python からも動く。ただしこれは**採用理由ではなく結果**である。

> **【メモ】2026-08-31：`run.py` は WSL 側（Sonar リポジトリ）へ移した**
> §3-3「コードは repo」に従い、`check/run.py` を `~/workspace/sonar/check/` へ移設した
> （正典 `src/prompt/system.md` を読ませるため。→[詳細設計書](../detail.md) §4-8）。
> **実行環境は WSL の `python3` になる**ので、上の副産物はもう使わない。
> キーは `WSLENV` 経由で WSL に届いているため、**この決定は変えなくてよい**——
> 前提（Windows で動かす）が消えても、採用理由（実体を1箇所に持つ）は無傷である。

> **【成果】通しで検証済み（2026-08-30）**
> | 確認 | 結果 |
> |---|---|
> | Windows の User 環境変数に登録されている | OK |
> | `WSLENV` が `ANTHROPIC_API_KEY/u` になっている | OK |
> | WSL 側へ全長で届く | OK（**ただし条件あり。下の落とし穴2**） |
> | **WSL から Anthropic API を叩ける** | **OK（HTTP 200 / `claude-haiku-4-5-20251001` / input 8 tok）** |
> | `~/.bashrc` `~/.zshrc` `~/.profile` `~/dotfiles` に書かれていない | OK |
>
> **`WSLENV` は変数名を指しているだけなので、キーを差し替えても設定し直す必要はない。**

> **【注意】途中で踏んだ落とし穴**
> `WSLENV` に**キーの値そのもの**を入れてしまい、WSL 側が `0` 文字を受け取る状態になった。
>
> **`WSLENV` は入れ物ではなく「運ぶ変数の名簿」である。** 書くのは値ではなく**変数名**（＋フラグ）。`WSLENV=sk-ant-...` は「その名前の変数を運べ」という指示になり、該当する変数が存在しないので何も運ばれない。
>
> **症状が「未設定」と見分けられない**のが厄介な点だった。どちらも `printenv` が空を返す。切り分けは、`WSLENV` の中身が**変数名として妥当か**を見ることでつく。

> **【注意】落とし穴その2：直すのは **WSL ではなく、WSL を起動している Windows アプリ**（2026-08-30 追記）**
> 上の検証表は「新しいターミナルを開いてから」実行したものだが、**その後に起動した別のセッションでは `ANTHROPIC_API_KEY` も `WSLENV` も空だった。** Windows 側（レジストリ）は正しいまま。
>
> **`WSLENV` の解決は `wsl.exe` の呼び出しごとに、呼び出し元 Windows プロセスの環境ブロックから行われる。**
> Windows プロセスの環境ブロックは**生成時に固定される**。`setx` はレジストリを書くだけなので、**それ以降に生成されたプロセスにしか反映されない。**
>
> したがって原因は「WSL が古い」ではなく「**WSL を起動している親プロセスが古い**」。直すのは親アプリである。
>
> | 手 | 効くか |
> |---|---|
> | ターミナルの**タブ**を開き直す | ❌ 同じアプリのプロセスから派生するので環境ブロックは古いまま |
> | `wsl --shutdown` | ❌ **不要かつ不十分。** VM を入れ替えても、起動し直す親アプリが古ければ何も変わらない |
> | **ターミナルアプリ（Windows Terminal / VS Code など）を終了して開き直す** | ✅ **これだけでよい。** 新しいプロセスがレジストリから環境ブロックを作る |
>
> 検証（2026-08-30 実測）：レジストリの値を明示的に持たせた PowerShell から `wsl -e bash` を叩くと、**動いている既存インスタンスに対してでも**キーは 108 文字で届いた。インスタンスの再起動は関係しない。
>
> ```powershell
> $env:ANTHROPIC_API_KEY = [Environment]::GetEnvironmentVariable('ANTHROPIC_API_KEY','User')
> $env:WSLENV            = [Environment]::GetEnvironmentVariable('WSLENV','User')
> wsl -e bash -c 'printenv ANTHROPIC_API_KEY | wc -c'
> ```
>
> **落とし穴1（`WSLENV` に値を入れた）と症状が同じ**——どちらも `printenv` が空を返す。切り分けの順序は
> ①Windows 側が正しいか（`[Environment]::GetEnvironmentVariable('WSLENV','User')`）→ ②正しければ**設定ではなく反映を疑い、親プロセスの生成時刻を見る**。
>
> **解消済み（2026-08-30 23:57）。** ターミナルアプリを開き直しただけで通った（キー長108、Anthropic API へ HTTP 200）。
> **このとき WSL の起動時刻は 23:48:40 のまま動いていない**——インスタンスを入れ替えずに直ったことが、上の「親プロセスがすべて」の実証になっている。

手順は §6。

### 3-6. `gh` は WSL 側に入れる

コードが WSL にある以上、提出物⑦のリポジトリ操作も WSL で完結させる。Windows の `gh.exe` を呼ぶと、**認証情報が Windows と WSL の2系統に分かれる**。実施は 8/31 のリポジトリ作成時でよい。

### 3-7. 開発サーバは `127.0.0.1:3100`（2026-08-30 実測で確定）

| 項目 | 決定 | 根拠 |
|---|---|---|
| バインドアドレス | **既定の `127.0.0.1` のまま** | Windows のブラウザから `http://localhost:3100` が 200 で返った。**`HOST=0.0.0.0` は不要**。ループバックに閉じるほうが安全なので、必要ないなら開けない |
| ポート | **3100**（Topcoat 既定の 3000 から変更） | **3000 は `yse_compass`（Next.js dev）が `*:3000` で占有している。** 既定のままだと `AddrInUse` で落ちる |

> **【注意】ポート3000で「通った」ように見える罠**
> 最初に `curl http://127.0.0.1:3000` が 200 を返したが、**それは Topcoat ではなく yse_compass の Next.js が返した HTML だった**（Topcoat 側は `AddrInUse` で panic 済み）。
> **ステータスコードだけ見ていたら、スパイク1を偽の合格にしていた。** 本文の中身まで確認する。

起動は `PORT=3100 topcoat dev`（アセットのバンドルには `topcoat-cli` が要る。→§6 手順4）。バイナリを選ぶときは `--bin <名前>`。

> **【注意】`topcoat dev` はアセット単体の変更を拾わない（2026-08-31 実測）**
> `.rs` を直すと再ビルド・再バンドル・再起動まで自動で回るが、**`.js` / `.css` だけを直しても再バンドルされない。** 古いハッシュのファイルが配られ続ける。
>
> **症状が「コードが間違っている」と見分けられない**——ブラウザは200を返し、中身だけが古い。切り分けは配信されている URL のハッシュが変わったかを見ること。**対処は dev サーバの再起動。**
>
> `mock/` の移植（9/3〜）は `.js` / `.css` を触る作業なので、ここで踏む。

> **【メモ】zsh の `=` 展開**
> `cargo install topcoat-cli --version =0.6.2` は zsh だと `=0.6.2` がコマンド名解決に食われて失敗する。**クォートする**（`--version '=0.6.2'`）。

### 3-8. ドキュメントは Vault を正典としたまま、コード側の `docs/` へ一方向に生成する（2026-08-31 追加）

§3-3 でリポジトリを分けた結果、**WSL 側の Claude Code はドキュメントを見に行けない。** 毎回 `/mnt/c` を辿って探させるのは、§3-2 と同じ種類のコスト——実装時間から直接引かれ、一度払えば済むものではない。

**`tools/build_docs.py`（Vault）が、正典から `~/workspace/sonar/docs/` を生成する。**

| | 正典 | `docs/` |
|---|---|---|
| 位置づけ | Vault の各ノート | **生成物。手で編集しない** |
| 直す場所 | Vault 側だけ | 直さない（次の生成で消える） |
| 反映 | — | Vault で `python3 tools/build_docs.py` を再実行する |

> **【重要】これは §8 の「`/mnt/c` に置き直す」への回答であって、リポジトリの統合ではない**
> 「Vault の中にあれば一緒に見られる」という圧力に、**ビルド時間を払わずに**答える手段が `docs/` である。
> 形は §3-4（`mock/` の一方向コピー）とまったく同じで、移すのは写しだけ、正典は動かない。
> **したがって §8 の「Vault と同じリポジトリにまとめる」には抵触しない。**

**手で置かない理由**は、置いた瞬間に同じ本文が2箇所に存在するから。これは 2026-08-31 に2度踏んだ事故（system プロンプトの二重管理 →[詳細設計書](../detail.md) §4-3／参照切れ →同 §4-8）と同じ構造である。したがって `build_basic_design.py` と同じく、**手編集はハッシュ照合で検出して生成を止める**（`tools/.docs.sha256`）。規律ではなく機械で守る。

**方向は一方向で、逆流させない。** WSL 側で気づいたこと（逸脱・罠・判断）は `docs/` に書かず、セッションの出力として報告し、[詳細設計書](../detail.md) / [次の作業の入口](../next.md) へ反映してから再生成で降ろす。`docs/` に書き戻せるようにすると「Vault と `docs/` のどちらが新しいか」が発生し、二重管理が復活する。

**収録するのは実装者に要るものだけ。** 学校提出のための文書（『企画書』・『基本設計書』・『理解度テストレポート』）は入れない。とくに 『基本設計書』 は5編の設計書からの生成物なので、収録すると生成物の生成物になる。「入っていないもの」とその理由は `docs/README.md` に出す——黙って落とすと、無いことに気づけない。

**`CLAUDE.md` はコード側に手で置く**（生成物ではない）。セッション開始時に自動で読まれるのはこのファイルだけなので、「まず `docs/README.md` を読む」「`docs/` は直さない」「気づきは報告する」の3点をここに書く。**これが無いと `docs/` は置いただけで読まれない。**

### 3-10. 開発機は2台ある（自宅・学校。2026-08-31 判明）

**§3-1〜§3-3 は開発機が1台である前提で書かれていた。** 実際には**自宅と学校の2台**で開発しており、同期は GitHub の `sonar` リポジトリ経由で行われている。

**決定：リポジトリを唯一の同期経路とする。** 機械ごとに違う状態を持たせない。

**リポジトリは2本ある。どちらもリモートを持つ。**

| リポジトリ | リモート | 同期 |
|---|---|---|
| コード | `250158hj-maker/sonar` | 手動 commit / push |
| **Vault（ドキュメント）** | `250158hj-maker/obsidian_vault` | **自動バックアップコミットが回っている** |

| 対象 | 同期されるか | 帰結 |
|---|---|---|
| `src/` `check/` `Cargo.*` | ✅ git（手動） | 通常の運用 |
| **Vault のノート** | ✅ **git（自動）** | 判断・設計書は**放っておいても届く** |
| **`sonar.db`** | ❌ **`.gitignore`** | **地図のデータは機械をまたがない。**発表用の地図は**デモ機（学校）で育てる**しかない |
| **`docs/`** | ⚠️ **git だが、生成が手動** | **ここだけが自動で流れない。**Vault が届いても、`docs/` は再生成 → commit → push しないと古いまま（→§3-8） |

> **【注意】「常に動く main」の意味が、2台になった時点で変わった**
> [スコープと縮退ライン](../scope.md) §0 は「スパイク成立後は**常に動く main** を維持する」と定めている。開発機が1台のときは「コミットしてある」で足りたが、**2台では「push してある」まで含まなければ成立しない。**
>
> 自宅で直して push を忘れると、翌日の学校は**古い `main` から始まる**。そこで直すと分岐が生まれ、片方を捨てる作業が発生する。**実装8日という予算に、その作業は入っていない。**

> **【注意】自動で流れないのは `docs/` だけ**
> Vault のノートは自動バックアップで両機に届く。**`docs/` だけが手動である。**`tools/build_docs.py` は **Vault → コード側 `docs/`** の一方向生成で（→§3-8）、走らせるのも commit するのも人間だから。
>
> **規則：Vault を直した機械で、その場で生成して両方を push する。**
> 場所を「直した機械」に固定するのは、**そのときだけ Vault が最新であることが自明だから**である。Vault が両機にある以上、**古い Vault から生成した `docs/` を新しいコミットとして載せる**経路が存在する。生成のタイミングを編集に密着させると、その経路が塞がる。
>
> やらないと、翌日の学校の Claude Code は**前日の判断を知らないまま**作業する。これは 2026-08-31 に2回踏んだ「台帳と実態の食い違い」と**同じ構造**である（→『理解度テストレポート』「本当の問題は、壊れたことを知る手段が無かったこと」）。**違いは、こちらは検知手段が既にあること**——`git status` に未コミットの `docs/*.md` が出る。

```bash
python tools/build_docs.py
```

> **【メモ】積み残し：`docs/` は同じ本文を2つのリポジトリに置いている**
> HUB は提出用ファイルについて「**生成物を vault に置くと同じ本文が2箇所に並ぶため、残すのは生成手段だけ**」と決めた（2026-08-31）。`docs/` は**同じ論理が当てはまる場所**である——Vault のノートと同じ本文が、`sonar` リポジトリにもコミットされている。
>
> **いまは直さない。** §3-8 は「WSL の Claude Code は Vault を見に行けない」という前提で置いた決定であり、その前提が**Vault のリモート化で崩れたのは 2026-08-31 である**。作り直すなら 9/15 の後。**フリーズ前に触る類の変更ではない。**

## 4. 決定の根拠（3視点）

- **開発者**：唯一の技術的争点は「C コンパイラをどこから持ってくるか」だった。WSL は既に持っており、Windows は数GB払って手に入れる。同じものに二度払わない
- **クライアント（評価者）**：見せる先は Windows のブラウザである。**WSL で動かしても、デモの見え方は変わらない**——ただし `localhost` で届くことが前提なので、スパイク1で確認する（→§5）
- **経営者**：実装8日・提出物制作7日（うち1日は GameB）という予算で、環境構築に半日以上を割く余地が無い。**既に動くものを使うのが最も安い**

## 6. 手順（8/31 の入口）

**1. APIキーを発行し、Windows の User 環境変数 `ANTHROPIC_API_KEY` に入れる**

作り直す場合は、**Claude Console で古いキーを失効させる**ところまでを1組の作業にする。新しいキーを作っただけでは、古いキーは有効なまま残る。

**2. WSL へ渡す**（Windows 側。PowerShell）

```
setx WSLENV "ANTHROPIC_API_KEY/u"
```

既に `WSLENV` に値がある場合は `:` で連結する（2026-08-30 時点では User・Machine とも未設定なので、そのまま実行してよい）。**新しいターミナルを開いてから**確認する。

```
wsl -e bash -lc "printenv ANTHROPIC_API_KEY | wc -c"
```

`0` 以外が返れば通っている。

**3. プロジェクトを作る**（WSL）

```
cd ~/workspace && cargo new sonar
```

**4. Topcoat CLI を入れる**（WSL。アセットのバンドルに要る）

```
cargo install topcoat-cli --version '=0.6.2'
```

`topcoat dev` がビルド・アセットのバンドル・起動をまとめて行う。**`cargo run` だけではアセットが配信されない**（バンドラが CLI 側にあるため）。クォートを外すと zsh の `=` 展開に食われる（→§3-7）。

**5. `mock/` をコピーする**（WSL）

**配置先は `~/workspace/sonar/src/`。** Topcoat のアセットは `asset!("./script.js")` で宣言し、**パスはそのマクロを書いたソースファイルからの相対**になる（`examples/asset` の規約）。配信は `/_topcoat/assets/script-<hash>.js` という content-hash 付きURLで行われる。

```
cp /mnt/c/Users/250158/Desktop/obsidian/Vault/01_projects/06_sonar/mock/{script.js,style.css} ~/workspace/sonar/src/
```

**コピーするのは `.js` と `.css` だけ。** `.html` はコピーせず、`view!` マクロへ書き写す（Topcoat がページを持つので、HTMLファイルは配信物ではなくなる）。`README.md` もコピーしない（→§3-4）。**コピーは9Pを通るが1回だけなので、遅くても構わない。**

> **【メモ】`view!` へ書き写すときの差分（2026-08-30 実測）**
> 値なしのブール属性は通らない。`<button hidden>` は **`hidden=(true)`** と書く（描画結果は `hidden=""` で HTML として等価）。属性値は**文字列リテラルか `(式)` のどちらか**でなければならない。

- [x] `~/workspace/sonar` —— **作成済み**（`cargo new` ／ `git init` 済み。リモートは未作成）

> **【成果】スパイク1・2 通過（2026-08-30）**
> **`mock/script.js` を1バイトも編集せずに配信でき、地図が実際に描画された。**
> → 正典 §6「マインドマップの実装方針」の**分岐は「通る」側に確定**。サーバ生成の静的SVGへの縮退は不要になった。

> | `style.css` が配信される | `text/css` / 31,424バイト / **md5 が完全一致** |
> | `initMap()` が完走する | ノード24個（`role="button"`＋`tabindex`）・枝24本・深さの目盛りを生成。`fitView()` が viewBox を `0 0 1000 700` → `-378 -47.45 756 411.4` に書き換え |

> | 見た目 | 根「わたし」＋会話7本、曲線の枝、浅い／深いの目盛り。**ラベルは根だけ**（→`mock/README.md` 設計の意図8・11 のとおり） |

> **【メモ】Topcoat のクライアントランタイムは注入されなかった**
> 地図ページの `<script>` は**我々の1本だけ**で、`_topcoat/runtime` への参照は無い。`$(...)` を使わないページには Topcoat がランタイムを載せないため。

- **ちらつき防止のインラインスクリプトを移していない。** `mock/*.html` は `<head>` で `data-theme` を描画前に当てているが、`view!` へは書き写していないため、初期表示がライト固定になる。9/3 の移植で対応する（`asset!` の別ファイルに出すか、`view!` の生HTML埋め込みを調べる）

## 8. 蒸し返さないこと

- **`/mnt/c` に置き直す**——「Vault の中にあればドキュメントと一緒に見られる」は必ず出てくる。払うのは毎回のビルド時間である（→§3-2）。**この動機は `docs/` の生成で解消済み**（→§3-8）
- **Vault と同じリポジトリにまとめる**——提出物⑦の要件で不可能（→§3-3）
- **移植後に Vault の `mock/` を直す**——直す先は Sonar 側だけ（→§3-4）
- **`.env` にキーを書く**——git に載る経路を作らない（→§3-5）
- **`docs/` を手で直す**——生成物であり、直しても次の生成で消える。直す先は Vault のノート（→§3-8）
- **`docs/` から Vault へ書き戻す仕組みを足す**——「どちらが新しいか」を発生させない。方向は一方向のまま（→§3-8）
