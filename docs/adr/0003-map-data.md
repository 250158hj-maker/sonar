## 1. 決定

### 1-1. 別々の会話のノードは合流させない

同じ話題が複数の会話に出てきても、**1つのノードにまとめない**。会話ごとに独立した枝のまま蓄積する。

結果としてデータは常に**木**になる。

### 1-2. 全体表示は会話単位で畳む

地図の全体表示に出すのは **各会話の1手目だけ**。押すとその会話の枝が開く。他の会話は畳まれた点として残る。

### 1-3. X座標は tidy tree で計算する

葉を左から順に並べ、親は子の中点に置く。Y座標は `根からの距離 × 一定間隔`。

### 1-4. 描画ライブラリは使わない（2026-08-26 追記）

上記はすべて**座標計算の話**であり、描画方法とは独立している。当初はライブラリの採否をスパイク2の後に決める予定だったが、**外部ライブラリを使わないことに決定した**。

`mock/` が依存ゼロのままパン・ズーム・会話単位の折り畳みまで到達しており、実装では `CONVERSATIONS` / `NODES` をDBのデータに差し替えるだけで済む。スパイク2が通らなかった場合はサーバ生成の静的SVGへ縮退し、そのときも `layout()` の座標計算は Rust へ移して再利用する。→[スコープと縮退ライン](../scope.md) §6

## 2. 文脈

### なぜ論点になったか

「全会話を1枚に蓄積する」と決めた（→[スコープと縮退ライン](../scope.md) §8）ことで、2つの未確定事項が生まれていた。

1. **ノードの統合ロジック** — 同じ話題をどう同一と判定するか
2. **ノードが増えたときのレイアウト** — モックは9ノード。数十になったときの配置

**この2つは同じ1つの問題だった。** 統合するかしないかで、使えるレイアウト方式が変わるためである。

### モックで測った破綻点

手置き座標のモック（9ノード）を計測したところ、当たり判定の直径は57px、必要な間隔は52ユーザー単位だった。会話が増えたときの試算は次のとおり。

| 会話数 | ノード数 | 同じ深さの最小間隔 | 当たり判定 |
|---|---|---|---|
| 7 | 39 | 67px | 57px |
| 20 | 101 | **22px** | 57px |
| 50 | 242 | **10px** | 57px |

**会話8〜10回で当たり判定が重なり始める。** ホーム画面が謳っている「話した回数7／地図に残った言葉23」が、ほぼそのまま上限だった。

「使うほど育つ地図」を売りにしている以上、これは端の話ではなく2ヶ月目の話になる。

## 3. 選択肢

| | 内容 | ノードが増えたとき | コスト |
|---|---|---|---|
| A | 全部を1枚に描き、パン／ズームを本気で実装する | 画面は有限なのでいつか必ず破綻 | 中〜大 |
| **B** | **全体表示を会話単位で畳む** | **1画面の点の数が会話数で決まる** | **小** |
| C | 期間で絞る（今月／今週） | 解決するが「蓄積が見える」価値を削る | 極小 |

そして B と直交する形で：

| | 内容 |
|---|---|
| **合流しない** | **会話ごとに独立した枝。木のまま** |
| 合流する | 同じ話題を1ノードに融合。DAG になる |

## 4. 根拠

### 4-1. 合流させない理由

**(a) 縦軸の定義が壊れる**

合流させると同じノードに複数の親が付き、木ではなく DAG になる。すると**根からの距離が経路によって変わる**。

地図の中心的な意味は「縦の位置＝その話題を何回掘り下げたか」である。深さが一意に決まらなくなることは、この地図の**意味そのものが定義できなくなる**ことを指す。

**(b) §6 でラベルを拒否した理由が、そのまま当てはまる**

`mock/README.md` では「『出来事』『信念』などのカテゴリ名を付けない」と決めている。理由は **ラベルを貼る行為＝本人の発話を分類すること＝弱い形の断定** だから。

「この2つの発話は同じ話題だ」も同じくAIの判断である。しかもこちらは、分類ラベルを貼るのではなく**地図の構造そのものとして断定する**ので、より強い。

> AIに「あなたの信念は〇〇です」と言わせないと決めておきながら、地図で同じことをやってはいけない

この一文が、そのまま合流を否定する。

**(c) 「たくさん会話が並ぶことに意義がある」と噛み合わない**

蓄積を見せたいのに、合流は「並んでいた別々の発話」を1点に畳む操作なので、**並ぶ量が減る**。目的に対して逆向きに働く。

**(d) 実装コストが最小になる**

木のままなら tidy tree（線形時間・重なりなし）がそのまま使える。DAG だと Sugiyama 法（層別レイアウト）が必要になり、DBもノードの親子が多対多になる。

### 4-2. B（畳む）を採る理由

A は有限の画面に無限のノードを載せようとしている以上、いつか必ず破綻する。C は解決するが価値そのものを削る。

B だけが「1画面の点の数が、ノード総数ではなく会話数で決まる」という性質を持つ。会話1回あたり3〜6ノード増えても、全体表示の密度はその1/3〜1/6でしか増えない。

**畳んだ会話が点として残り続けるのが要点で、会話が並んでいること自体が地図の中身になる。**

縮退ラインとしても優秀で、間に合わなければ「会話一覧＋個別マップ」の形で提出できる。

---

## 5. B だけでは足りない部分

正直に書いておく。**B は破綻点を先送りするだけで、消しはしない。**

全体表示の点の数は会話数に比例して増え続けるので、どんな画面も有限である以上いつかは入り切らない。そこで2つ足した。

- **縮尺に下限を設ける**（`MIN_GAP_PX = 58`）。点の間隔が58pxを切るところまでは引かない
- **入り切らない分はドラッグで動かす**（パン）

40会話（159ノード）で確認したところ、全体表示に出るのは41点、点の間隔は58px、当たり判定は48pxで重ならずに保たれた。

**会話が数百件になったら、期間で区切る（選択肢C）のが次の手。** ただし「蓄積が見える」価値を削るので、実際に困るまで入れない。

## 6. 決定の帰結

| 領域 | 内容 |
|---|---|
| DB設計（提出物⑥） | ノードの親は1つ。`parent_id` の自己参照でよい。多対多の中間テーブルは要らない |
| 深さの保持 | **保存しない。** 木なので `parent_id` を辿れば一意に決まる。持つと二重管理になる |
| レイアウト | tidy tree。`mock/script.js` の `layout()` がそのまま移植できる |
| 描画 | **`mock/` のコードを移植**。外部ライブラリなし（→§1-4）。座標計算とは独立なので、描画だけ後から差し替えられる |
| プロンプト設計 | 「この発話は既存のどのノードと同じか」を判定させる処理が**不要になった**。呼び出しが1つ減る |

## 6-2. 追記：全体表示は放射に変えた（2026-08-31）

§1-3「X座標は tidy tree で計算する」を、**全体表示に限って**改める。

| 状態 | レイアウト |
|---|---|
| **全体表示** | **わたしを中心とした同心円。** 会話の1手目を円周に等間隔で置く |
| 会話を開いた | 従来どおり tidy tree（縦軸＝根からの距離） |

### なぜ分けたか

**overview と detail は違う問いに答えている。**

全体表示が答えるのは「どれだけ積み上がったか」。ここで見えているのは根と各会話の1手目だけで、
**1手目はすべて深さ1**である。つまり**表すべき深さが存在しない**のに、縦軸を深さに使っていた。
その結果、深さが1段しかない画面に「会話の点の列をちょうど貫く破線」と
左端の「浅い／深い」の軸が出ていた（同時に削除）。

会話を開いて初めて「どこまで掘り下げたか」の問いになり、そこで縦軸が要る。

### §7 のトリップワイヤには触れていない

§7 は「覆すとしたら**縦軸＝深さをやめる**ときだけ」としているが、
**全体表示にはもともと表す深さが無く、会話を開けば縦軸＝深さのまま**である。
やめてはいない。だから新規 ADR ではなく本 ADR への追記とする。

（全体表示でも深さを半径で表す——中心からの距離＝深さ——という案は別物で、
そちらを採るなら §7 のとおり新しい ADR を起こす。）

### §5「B は破綻点を先送りするだけ」への効き

1列に詰めると1画面に入る会話数は画面幅で決まる。同心円は2次元に詰めるので、
同じ下限（`MIN_GAP_PX = 58`）のまま入る数が増える。

| | 1画面に入る会話数 |
|---|---|
| 横一列（従来） | **23本** |
| 同心円 | **84本** |

**破綻点は消えていない。** 3.6倍先へ動いただけで、§5 の「期間で区切るのが次の手」は生きている。

### 副産物：初期位置の判断が不要になった

横一列では、入り切らないときに「古い側と新しい側のどちらを映すか」を決める必要があった
（実測30会話で両端8本が画面外、うち最新の会話も外）。
**わたしが中心にいる限り、この問いは発生しない。**

## 7. 蒸し返さないこと

- 「同じ話題をまとめたほうが賢く見える」——見た目の話であり、縦軸の定義を壊す対価に見合わない
- 「グラフDBを使えば合流できる」——できるかどうかではなく、**やるべきかどうか**を否定している
- 「全体表示に全ノードを出したほうが蓄積が伝わる」——測定済み。会話20回で押せなくなる

将来これを覆すとしたら、**「縦軸＝深さ」をやめる**ときだけ。そのときは ADR を新しく起こす。
